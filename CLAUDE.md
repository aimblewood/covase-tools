## 1. What this is

**ORBIS-SON** is Covase Ltd's internal fleet-management platform: short-hire bookings, CRM, vehicle movements (logistics), accident claims (FMG), fines & penalties, invoicing. Goal: fully detach from Dynamics 365 within months. Built and maintained conversationally with Claude; Simon Homer is the owner/operator and the only person who pushes deploys.

**Stack:** vanilla HTML/JS app — `covase-platform.html` is the page shell (markup only, ~210KB); styles live in `css/platform.css` and the script in `js/01-core.js` … `js/08-chrome.js`, one file per area (core/config/Dynamics/Supabase, invoices, hires, movements, CRM, claims, fines, chrome = edit mode/fonts/realtime/sidebar/mobile). They are classic `<script src>` tags loaded in that order, so every function is still a global and inline `onclick=` handlers work unchanged; split 2026-10-21 byte-for-byte from the old single file (concatenating the js files gives the old `<script>` exactly). **Load order matters:** code that runs at load in file N must not call something declared only in a later file. + Supabase (Postgres/PostgREST/Realtime/Storage via anon key) + n8n cloud for automation + Microsoft Graph for email + Claude API for extraction/classification. Deployed on **GitHub Pages**: repo `aimblewood/covase-tools` → https://aimblewood.github.io/covase-tools/. **Push = deploy.** Rollback = revert commit (or `covase-platform.old.html` snapshot).

**Live system.** Colleagues use it daily and the Supabase project is shared/production. UI iteration is safe; data experiments are not. Never run destructive SQL without Simon's explicit confirmation.

**n8n editing rules (hard-won):**
- `update_workflow` **merges** parameters — nested objects (e.g. `queryParameters`) must be fully replaced, and removing a field means explicitly setting its parent off (`sendQuery:false`).
- **Always `publish_workflow` after edits** — updates are drafts.
- Code-node sandbox: no `fetch`; use `this.helpers.httpRequest` + `$vars`. **`helpers.httpRequest` JSON-serialises Buffer bodies** — binary uploads must go through an HTTP Request node with `contentType:'binaryData'`. Code nodes have a **60s task cap** — batch long loops.
- Graph: subfolders need `/mailFolders/inbox/childFolders`; no `$select=contentBytes` on base attachment type; 429s → node batching + retryOnFail. Lex PDFs arrive as `application/octet-stream` — detect by filename too.
- **Execution budget rules in PROJECT.md §11 are law** — no polling faster than 15 min without doing the maths for Simon; never activate a new workflow yourself.

Rows live in memory + a per-machine localStorage copy, never the DB. Per car at the chosen term/mileage: WLC = finance + service + irrecoverable VAT (10% of finance) + lease rental restriction (15% × (finance+VAT) × client corp tax, only above 50g/km for post-Apr-2021 regs) + employer's NI (15% × BIK value, **term-average by default**, first-year option) + fuel/energy (+ insurance if the policy sets it). **BIK is automated for PHEVs**: 0g → zero row; 1–50g → electric-range bands; **>50g → normal CO₂ table whatever the range** (the Stihl workbook had hand-typed range-band rates on 221 of 375 PHEVs that are actually >50g under the new Euro 6e-bis figures — e.g. BMW M5 10% typed vs 28%); diesel +4% unless RDE2, capped at that year's top CO₂ rate. A PHEV with no electric range is refused, not guessed. Verified: all 679 EVs in the Stihl workbook match its WLC to the penny with NI on first-year basis. Client policies (`covase_config` `wlc_policies`: fuels, min EV/PHEV range, max CO₂/P11D, brand list, excluded wording, grades with budgets monthly or over term, cumulative or banded, PHEV MPG % (Stihl 60%), EV range %, **payment profile + commission**) and tax tables/fuel prices (`wlc_settings`, seeded from the Stihl workbook, editable, + Add a tax year). **Payment profiles** (Simon, 28 Oct): the ratebook's `Payment_Plan` (e.g. "Spread Rentals with 6 down" = 6+(term−1) = 53 payments on 48m; "3+35" = 38; terminal pause = term) is read per row; the policy's profile (as ratebook / spread N down = N+term−1 / terminal pause N down = term payments) re-divides the contract total, so finance and service × src/dst payments. **Commission** (£, whole contract) ÷ the client's payment count is added to the **finance rental only** (so it also carries irrecoverable VAT and LRR). A plan ORBIS can't read, or a file with no plan column, is refused when a conversion or commission is asked for. WLC over term = rental items × payment count + NI/fuel/insurance × term. **Energy/fuel** (Simon, 29 Oct): EV cost = miles ÷ (range ÷ kWh × EV range %) × elec £/kWh, used directly. Simon's workbook got there via a hand-tuned 'factor' (29.11) in MPGe = mi/kWh × factor, nudged until Y (true energy cost), AA (MPGe fuel cost) and AB matched. That factor is just petrol £/gal ÷ elec £/kWh, so ORBIS works it out (`clMpgeFactor`) and only uses it to show a cost-equivalent **MPGe** column (table + working sheet) for clients' fuel-economy columns. Prices carry `fuel_as_of` / `elec_as_of`; the list warns when fuel is >7 days old or electricity predates the current Ofgem quarter (1 Jan/Apr/Jul/Oct). Prices are still typed in (links to RAC Fuel Watch and the Ofgem cap); the browser can't fetch those sites itself. **Battery rules** (`battery_rules` in `wlc_settings`, seeded with Simon's Tesla figures) fill kWh only when neither the file nor the description has one; every word must appear, most words wins, equally specific rules that disagree → flagged. Results table: click any heading to sort, a filter box under each heading (words, or `>300` / `<500` / `300-400` / exact on number columns; BIK columns in %), and a top search matching every word in any order across make/model/fuel/body/CAP/grade/notes; these re-draw only (no re-calc) and keep the cursor in the box. Exports ignore the table filters. Outputs: working sheet XLSX (all sums), driver lists print/PDF and XLSX per grade — vehicle + BIK % + monthly tax at 20/40(/45)% per tax year, **never WLC**.
- **Email templates** (Settings): hire booking (WYSIWYG), offhire, movement, fines driver emails, both agent instruction editors. All send modals show rendered subject+body, freely editable, ↻ rebuild, job ref auto-appended to subject.

**Job refs:** every hire `CVB-nnnn`, movement `CVM-nnnn` — shown in modals/cards, carried in email subjects, and the reply agents' primary match key. Never strip them from subjects. `composeToSupplier()` inherits its subject from the last outbound row, so `withJobRef()` re-stamps any inherited subject missing its ref — without it, a thread whose last outbound was a manual reply or auto-ack went out with no ref and the answer came back unmatched.
